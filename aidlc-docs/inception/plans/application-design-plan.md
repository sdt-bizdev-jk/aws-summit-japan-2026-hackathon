### Q1: コンポーネント粒度（バックエンド）
Django アプリケーションの分割粒度をどうしますか？

- A) 機能ドメイン別に分割（trips, analysis, notifications, social の4アプリ）
- B) コア + 補助で分割（core に旅・途中下車・景色、auxiliary に分析・通知・ソーシャル）
- C) モノリシック（1つの Django アプリに全モデル・ビュー）

[Answer]: A

### Q2: AI連携の設計パターン
Bedrock（Claude）との連携をどのように抽象化しますか？

- A) 専用サービスクラス（AIService）に全AI呼び出しを集約し、プロンプトテンプレートを管理
- B) 各機能コンポーネント内にAI呼び出しを分散配置（道標生成は trips 内、横断分析は analysis 内）
- C) AI呼び出しを共通基盤（AIService）+ 機能別プロンプト管理（各コンポーネントがプロンプトを定義し、AIServiceに渡す）

[Answer]: Aでいいと思っています。 utils/ai_generator.py とかにAI関連のクラスを集約する形で。

### Q3: フロントエンドのコンポーネント構成
Next.js フロントエンドの画面構成をどうしますか？

- A) ページベース（pages/: home, trip-start, trip-detail, analysis, timeline）— シンプルなルーティング
- B) App Router + レイアウト共有（app/: (main)/home, (main)/trips/[id], (main)/analysis, (main)/timeline）— Next.js 13+ の推奨パターン

### Q4: 通知サービスの独立性
プッシュ通知の仕組みをどの程度独立させますか？

- A) 独立サービス（NotificationService）— スケジューラー含む、バックグラウンドタスクとして動作
- B) Django管理コマンド + cron/CloudWatch Events — シンプルに定期実行で通知判定
- C) 旅コンポーネント内に組み込み — 進捗報告時やフェードアウト判定時にインラインで通知

[Answer]: アプリ側から通知のタイミングを設定とかできると良いかな、とは思っています。なので定期実行にはならないんでしょうかね？人によっては20時にリマインド、19時にリマインド、とかを想定しています。

## フォローアップ質問

回答分析の結果、以下の点について追加確認が必要です。

### FQ1: 通知サービスの確認（Q4の明確化）
Q4の回答から「ユーザーごとに通知時刻を設定でき、その時刻にプッシュ通知を送る」仕組みが必要と理解しました。
これは以下の設計になります:

- Django の `notifications` アプリ内に NotificationScheduler を実装
- ユーザーが旅ごとに通知時刻を設定（例: 20:00）
- ECS タスクスケジューラー（または CloudWatch Events + Lambda）で定期的に通知対象を判定・送信

この理解で合っていますか？

- A) はい、その理解で合っています
- B) いいえ、もっとシンプルでいい（固定時刻 or 1日1回の一括送信で十分）
- C) 別の方式を考えています（説明してください）

[Answer]: ああ、そういうことになりますね。つまるところ普通のバッチ処理になるわけですかね。まあここは優先度が高くないとは思うのですが、一応Aで。

### FQ2: ソーシャル機能のデータフロー（Q5の明確化）
PoC規模（〜100人）を考慮すると、各選択肢のメリットは:

| 方式 | メリット | デメリット |
|---|---|---|
| A) 単純DB読み取り | 実装最速、PoC向け | スケールしない |
| B) イベント駆動 | 将来のスケール対応、書き込みと読み取りの分離 | PoC段階ではオーバーエンジニアリング |
| C) キャッシュベース | 読み取り高速 | キャッシュ管理の複雑さ |

PoC規模では **A（単純DB読み取り）** が最もシンプルで十分ですが、将来を見据えて **B** にする価値もあります。どちらにしますか？

- A) 単純DB読み取り（PoC最速、シンプル）
- B) イベント駆動（将来対応、やや複雑）

[Answer]: ならAにとどめておきますか。
