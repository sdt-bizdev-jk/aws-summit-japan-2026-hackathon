# cycle-6 Requirements Clarification Questions

最初の回答ありがとうございます。Q4「戻れた率」と Q5「集中復帰までの平均秒数」について、計測意義への鋭い指摘をいただきました。これらの指標が「意味のある数字」になるよう、定義を確定させたいです。以下にお答えください。

---

## 背景: なぜ追加質問するか

現状の WaitLess は **AI 完了を検知すると自動で AI タブをアクティブ化** します (`wait_orchestrator.js` の `onCompletionDetected`)。そのため:

- **戻れた率 (Q4=A)**: 自動戻りはほぼ必ず成功するので「ほぼ 100%」になり、指標として面白みがない (ユーザー指摘の通り)
- **集中復帰秒数 (Q5=A)**: 「完了→自動アクティブ化」は一瞬なので、ほぼ 0 秒になり意味が薄い (ユーザー指摘の通り)

ユーザーは Q5 で「スクロールなどの動作を検知するまでのタイミングの方がいい」と提案されました。これを踏まえ、より意味のある指標を定義します。

---

## Clarification 1: 「戻れた率」をどう意味のある指標にするか

「自動で戻る」のは前提として、その後 **ユーザーが本当に AI 作業に復帰したか** を測る方が有意義です。どの定義を採用しますか?

A) **戻れた率は廃止** し、代わりに「**離脱継続率**」を測る = AI タブに自動で戻された後も、ユーザーがすぐ娯楽タブへ再離脱せず AI 画面に留まった割合
B) **戻れた率を「自動復帰成功率」として残す** = 完了検知時に AI タブが消えていた等で戻れなかった例外ケースのみを分母に取り、システムの信頼性指標として使う (ほぼ100%だが「失敗ゼロ」を示す健全性メトリクスとして表示)
C) **戻れた率を「自発的復帰率」に再定義** = AI 完了より「前に」ユーザーが自分から AI タブへ戻っていたサイクルの割合 (待ちきれずに自分で戻った=能動的、という行動指標)
D) Q4=A のまま「自動復帰率」で良い (ほぼ100%でも健全性の証明として表示する)
X) Other (please describe after [Answer]: tag below)

[Answer]: A

## Clarification 2: 「集中復帰までの平均秒数」の計測起点・終点

ユーザー提案の「スクロール等の動作検知」を採用する場合、AI タブに戻ってから **どのユーザー操作** を「集中復帰」とみなしますか? (Claude.ai タブ上の Content Script で検知)

A) AI タブ復帰後、最初の **スクロール / マウス移動 / キー入力 / クリック** のいずれかを検知した時点 (どれか早いもの)
B) AI タブ復帰後、最初の **キー入力 (テキスト入力開始)** を検知した時点 (実際に次のプロンプトを書き始めた=本当の復帰)
C) AI タブ復帰後、最初の **スクロール** を検知した時点 (出力を読み始めた=復帰)
X) Other (please describe after [Answer]: tag below)

[Answer]: A

## Clarification 4: VS Code (Kiro) 側の集中復帰秒数の扱い

Q7=B で VS Code 側も統計対象に含めると回答いただきました。ただし VS Code 側はブラウザのような「スクロール検知」がしづらいです。VS Code 側の集中復帰秒数はどうしますか?

A) VS Code 側は「完了→Kiro 最前面化」までの秒数のみ記録 (ブラウザ側のような操作検知はしない、簡易版)

X) Other (please describe after [Answer]: tag below)

[Answer]: B
