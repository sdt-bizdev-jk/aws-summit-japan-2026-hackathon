## プロジェクト概要

### テーマ
AWS Summit Japan 2026 AI-DLCハッカソン「人をダメにするサービス」

### サービス名: たびたび
「度々（たびたび）」と「旅々」のダブルミーニング。何度もやめてしまう（度々）ことが、何度も旅に出ている（旅々）ことと同義になる。サービスの核心構造「ダメなほど豊かになる」がタイトルに凝縮されている。

### コンセプト
「やめること」を前提に何かを始め、やめたときに「得たもの」を可視化して、挫折を肯定するサービス。
三日坊主を繰り返すほどサービスが賢くなり、「次に始めたら面白そうなこと」の提案精度が上がる。

**核となる思想:**
1. やめたこと自体に価値がある（ゼロではない）
2. 蓄積は消えない（やった分は残っている）
3. バラバラに見える挫折に、実は方向性がある
4. ダメであればあるほど、次の一歩の精度が上がる

**サービスの構造:**
- **入口（ダメさの肯定）**: やめた。それでいい。
- **蓄積**: やめた旅が溜まっていく。始めた数が増える。
- **出口（ポジティブな変化）**: 溜まった旅のパターンから「次に始めたら面白そうなこと」をAIが提案する。またやめていい前提で。

### メタファー: 旅

サービスの思想と旅の性質が構造的に対応する：

| サービスの思想 | 旅の必然性 |
|---|---|
| やめたことに価値がある | 目的地に着かなくても、歩いた道は存在する |
| 蓄積は消えない | 通った道は地図に残る |
| バラバラの挫折に方向性がある | 複数の旅路を重ねると、よく向かう方角が浮かぶ |
| ダメなほど次が良くなる | 多くの旅に出た人ほど、次の旅先選びが上手くなる |

### 絶対にやらないこと
- 長く続けた人を褒める
- 蓄積量（距離・日数）を比較する
- 「もっと続けられたはず」と示唆する
- 「次こそ続けよう」と圧をかける

## 機能要件

### FR-01: 旅に出る（始めるとき）
- ユーザーが「何か始めたい」と宣言する（テンプレ選択 or 自由入力、30秒以内で完了）
- AIが道標（「ここまでやったらこの景色が見える」）を自動生成して提示
- ゴール設定はしない。続けるプレッシャーはゼロ

### FR-02: 道中（やってる間）
- 基本的に追跡・管理はしない
- 道標ベースの軽いプッシュ通知を行う
  - 例:「あと1回走ると"自分のペース発見"の道標です。走っても走らなくてもいいですけど。」
- ユーザーが自分から進捗を報告することもできる（任意）

### FR-03: 途中下車（やめたとき）
- 自分から「降りる」と宣言する、またはフェードアウト後にそっと確認（3日間無活動で途中下車候補）
- AIが「道中で見た景色（得たもの）」を候補として提示。ユーザーはそのまま採用/編集/追加できる
- 一覧に追加される
- 旅の数カウントが増える（肯定的に）

### FR-04: 一覧画面（メイン画面）
- 途中下車した旅の一覧がメイン画面
- 各旅に「道中で見た景色」が紐づいている
- メイン指標: 旅の数（始めた回数）— 多いほど豊か

### FR-05: 横断分析 + 次の旅先提案
- 複数の旅を横断して「あなたが本当は何を求めていたか」のパターンをAIが発見
- パターンに基づいて「次に始めたら面白そうなこと」を提案
  - 例: 筋トレ3日 + ランニング2日 + ヨガ1日 → 「体を動かす系に何度も出かけてますね。"散歩"はどうですか？一番ハードル低いし、やめても景色は見てます」
  - 例: ギター1週間 + ピアノ3日 → 「音楽の旅が多いですね。"鼻歌を録音する"だけの旅はどうですか？」
- 提案は常に「またやめていい」前提
- 三日坊主を繰り返すほど提案精度が上がる

### FR-06: ソーシャル機能（軽量）
- 他のユーザーの途中下車が匿名でタイムラインに流れてくる
- 「自分だけじゃない」という安心感を提供
- PoC段階では最小限の実装（閲覧のみ、リアクションなし）

### FR-07: プッシュ通知
- 道標ベースの軽い通知（PWA Push Notification）
- 圧をかけない文面（「走っても走らなくてもいいですけど」）
- フェードアウト確認通知（3日間無活動後）

## 非機能要件

### NFR-01: プラットフォーム
- **PWA（Progressive Web App）**
- Webブラウザベースだがモバイルアプリ的な体験を提供
- ストア申請不要、プッシュ通知対応

### NFR-02: 認証方式
- **完全匿名（デバイスID紐付け）**
- アカウント作成不要
- フロントエンドで `crypto.randomUUID()` により UUID を生成し localStorage に保存
- 全APIリクエストに `X-Device-ID` ヘッダーとして付与
- 各モデルが `device_id: UUIDField(db_index=True)` を直接保持（Device テーブルは不要）
- 機種変更時のデータ移行は対象外（PoC段階）

### NFR-03: ユーザー規模
- **小規模（〜100人）** — ハッカソンデモ / PoC

### NFR-04: 言語
- **日本語のみ**

### NFR-05: パフォーマンス
- 旅の開始操作は30秒以内で完了できること
- AI応答は10秒以内（Bedrock API呼び出し含む）

### NFR-06: セキュリティ
- PoC段階のためセキュリティ拡張ルールはスキップ
- 最低限のデータ保護（デバイスIDの匿名性維持）

## 設計思想

1. **「やめていい」が大前提** — 続けるプレッシャーを一切かけない
2. **「通った道」の可視化が核** — やめたことの価値を認める
3. **始めた回数を肯定する** — 三日坊主の人ほど数字が増え、それが豊かさ
4. **ダメなほど次が良くなる** — 三日坊主を繰り返すほどAIの提案精度が上がる
5. **再開を強制しない** — 「次の旅先」は提案するが、行くかどうかはユーザー次第
6. **最小限の手間** — アカウント作成不要、30秒で出発、管理・追跡しない
