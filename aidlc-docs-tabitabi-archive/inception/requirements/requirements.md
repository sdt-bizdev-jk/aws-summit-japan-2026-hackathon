## プロジェクト概要

### テーマ
AWS Summit Japan 2026 AI-DLCハッカソン「人をダメにするサービス」

### サービス名: たびたび
「度々（たびたび）」と「旅々」のダブルミーニング。何度もやめてしまう（度々）ことが、何度も旅に出ている（旅々）ことと同義になる。サービスの核心構造「ダメなほど豊かになる」がタイトルに凝縮されている。

### コンセプト（比喩なし説明）

**三日坊主肯定サービス — 「人をダメにする」サービス**

三日坊主でいい。続けられなくていい。「続けられない自分」をそのまま肯定する。
このサービスは「やめること」を前提に何かを始め、やめたときに「得たもの」を可視化する。続けることを目指さない。

- 何かを始めて、やめる。それだけでいい。やめていい。
- やめたとき、AIが「あなたがそこで得たもの」を言語化してくれる。
- 三日坊主を繰り返すほど、AIが「次に始めたら面白そうなこと」を提案してくれる。精度は回数に比例する。
- 「ダメな人」ほどサービスが賢くなる。それがこのサービスの核。
- 「卒業」も「克服」もしない。三日坊主のまま、それでいい。

**核となる肯定:**
- 「挫折」ではない →「途中下車」しただけ
- 「続かなかった」のではない →「ここまでで得たものがある」
- 「ゼロからやり直し」ではない →「前回の分は残ってる」
- 「三日坊主」は欠点ではない →「旅の数が多い人」

### メタファー: 旅

サービスの思想と旅の性質が構造的に対応する：

| サービスの思想 | 旅の必然性 |
|---|---|
| やめたことに価値がある | 目的地に着かなくても、歩いた道は存在する |
| 蓄積は消えない | 通った道は地図に残る |
| バラバラの挫折に方向性がある | 複数の旅路を重ねると、よく向かう方角が浮かぶ |
| ダメなほど次が良くなる | 多くの旅に出た人ほど、次の旅先選びが上手くなる |

### 用語体系

| 概念 | 旅メタファー | 備考 |
|---|---|---|
| 何か始める | 旅に出る | |
| やってる間 | 道中 | |
| やめる | ここで降りる / 途中下車 | |
| 得たもの | 道中で見た景色 / 通った道 | |
| 一覧画面 | 旅の記録 | **確定** |
| 横断分析 + 次の提案 | あなたの方角 | **確定** |
| マイルストーン | 道標（みちしるべ） | |
| 蓄積の指標 | 旅の数（始めた回数） | 距離ではなく回数を肯定 |

### 絶対にやらないこと
- 長く続けた人を褒める
- 蓄積量（距離・日数）を比較する
- 「もっと続けられたはず」と示唆する
- 「次こそ続けよう」と圧をかける

## 機能要件

### FR-01: 何かを始める（旅に出る）
- ユーザーが「何か始めたい」と宣言する（テンプレ選択 or 自由入力、30秒以内で完了）
- AIが小さな区切り＝道標（「ここまでやったらこれが得られる」）を自動生成して提示
- ゴール設定はしない。続けるプレッシャーはゼロ

### FR-02: やってる間（道中）
- 基本的に追跡・管理はしない
- 道標ベースの軽いプッシュ通知を行う
  - 例:「あと1回走ると"自分のペース発見"の道標です。走っても走らなくてもいいですけど。」
- ユーザーが自分から進捗を報告することもできる（任意）

### FR-03: やめたとき（途中下車）
- 自分から「やめる」と宣言する、またはフェードアウト後にそっと確認（3日間無活動で途中下車候補）
- AIが「そこで得たもの」（＝道中で見た景色）を候補として提示。ユーザーはそのまま採用/編集/追加できる
- 「旅の記録」に追加される
- 始めた回数（＝旅の数）カウントが増える（肯定的に）

### FR-04: やめたものの一覧 — メイン画面（旅の記録）
- やめたものの一覧がメイン画面
- 各項目に「そこで得たもの」が紐づいている
- メイン指標: 始めた回数（＝旅の数）— 多いほど豊か

### FR-05: 横断分析 + 次の提案（あなたの方角）
- やめたものを横断して「あなたが本当は何を求めていたか」のパターンをAIが発見
- パターンに基づいて「次に始めたら面白そうなこと」を提案
  - 例: 筋トレ3日 + ランニング2日 + ヨガ1日 → 「体を動かす系を何度も始めてますね。"散歩"はどうですか？一番ハードル低いし、やめても得るものはあります」
  - 例: ギター1週間 + ピアノ3日 → 「音楽系が多いですね。"鼻歌を録音する"だけ始めてみるのはどうですか？」
- 提案は常に「またやめていい」前提
- 三日坊主を繰り返すほど提案精度が上がる

### FR-06: ソーシャル機能（軽量）
- 他のユーザーの「やめた」が匿名でタイムラインに流れてくる
- 「自分だけじゃない」という安心感を提供
- PoC段階では最小限の実装（閲覧のみ、リアクションなし）

### FR-07: プッシュ通知
- FCM（Firebase Cloud Messaging）によるプッシュ通知
- 道標ベースの軽い通知
- 圧をかけない文面（「走っても走らなくてもいいですけど」）
- フェードアウト確認通知（3日間無活動後）
- ユーザーごとの通知時刻設定

## 非機能要件

### NFR-01: プラットフォーム
- **React Native（Expo Managed Workflow）**
- iOS / Android ネイティブアプリ
- Expo によるビルド・配信（EAS Build / EAS Submit）
- OTAアップデート対応（Expo Updates）

### NFR-02: 認証方式
- **完全匿名（デバイスID紐付け）**
- アカウント作成不要
- デバイス固有IDを生成し SecureStore に保存
- 全APIリクエストに `X-Device-ID` ヘッダーとして付与
- 機種変更時のデータ移行は対象外（PoC段階）

### NFR-03: ユーザー規模
- **小規模（〜100人）** — ハッカソンデモ / PoC

### NFR-04: 言語
- **日本語のみ**

### NFR-05: パフォーマンス
- 旅の開始操作は30秒以内で完了できること
- AI応答は10秒以内（Bedrock API呼び出し含む）

### NFR-06: セキュリティ
- フルセキュリティ構成を採用
- WAF + Shield（フロントセキュリティ）
- Inspector（脆弱性スキャン）
- GuardDuty（脅威検知）
- CloudTrail（APIアクティビティログ）

### NFR-07: 監視・ログ基盤
- Fluentd → Kinesis Data Firehose → Elasticsearch + Kibana
- CloudWatch（メトリクス・ログ監視）
- AWS Config（構成管理・コンプライアンスチェック）
- Slackアラート連携（CloudWatch Alarm → SNS → Slack）

## アーキテクチャ概要

### データフロー

1. **モバイルユーザー**
   `React Native App → ALB Ingress → WAF/Shield → Backend Worker（EKS）→ DocumentDB / Lambda`

2. **生成AI連携**
   `Backend Worker → Amazon Bedrock`

3. **DWH連携**
   `AWS → Snowflake（横断分析・BI基盤）`

4. **プッシュ通知**
   `Backend Worker → FCM → React Native App`

5. **ログ・イベント**
   `Fluentd（EKS各Pod）→ Kinesis Data Firehose → Elasticsearch + Kibana`

6. **監視・セキュリティ**
   `CloudWatch / Inspector / GuardDuty → SNS → Slack`

### Worker構成

| Worker | 役割 | スケーリング |
|---|---|---|
| App Worker | PC向けWebアクセス（将来拡張用） | HPA |
| Backend Worker | モバイルAPI + バッチ処理（道標生成、フェードアウト検知、横断分析） | HPA |

## 設計思想

1. **「やめていい」が大前提** — 続けるプレッシャーを一切かけない
2. **「通った道」の可視化が核** — やめたことの価値を認める
3. **始めた回数を肯定する** — 三日坊主の人ほど数字が増え、それが豊かさ
4. **ダメなほど次が良くなる** — 三日坊主を繰り返すほどAIの提案精度が上がる
5. **再開を強制しない** — 「あなたの方角」は提案するが、行くかどうかはユーザー次第
6. **最小限の手間** — アカウント作成不要、30秒で出発、管理・追跡しない
